# 04 边界案例清单

状态：待填写。首日目标30个**具体、可复查的输入与预期结果**，用于开发契约验证，不是30个独立真实项目或正式效果测试集。

## 数量与选例

- 10条规则每条至少2例，合计至少20例；另外至少10例覆盖关键边界，总计30例。
- 覆盖普通满足、明确违反、阈值边界、已确认缺失、证据未知、例外/不适用、口径或版本冲突。具体分布按真实规则决定，不为凑分类编造政策。
- 至少有可预期PASS、FAIL和NEED_HUMAN_REVIEW的案例；例外/不适用若真实存在必须覆盖。没有WARNING类规则不必强凑。
- 不允许预期写“PASS或HUMAN均可”。业务口径未确认的案例标待定，不计入30例；已明确“因证据不足必须HUMAN”的案例可以计数。
- 构造样例标记修改点、来源包与原文件版本，留在开发集；正式盲测不能使用团队已反复调试的这些案例。

## 案例详情卡：每个复制填写一份

### CASE-待填

- 对应规则ID/版本：待填。
- 输入位置：包ID、文件ID/版本、页码、具体原文片段或受控截图位置；多文件比较列出两处。
- 构造变更：待填；真实未改写填“无”，构造例必须写修改了什么。
- 前置条件：政策适用性、例外状态、材料包是否提交完整、文件是否可读、已检查范围。
- 观察值：原始字段/单位/标签/时间口径；未知明确写未知，不自行补值。
- 唯一预期结果：PASS / FAIL / NEED_HUMAN_REVIEW / NOT_APPLICABLE / WARNING / SYSTEM_ERROR，选择与具体场景匹配的一项。
- 正确理由：引用真实政策和上述输入，解释为什么得出该结果。
- 应展示的证据/提示：待填；缺件可引用完整材料清单及缺失义务，不编造不存在的附件页码。
- 不允许出现的错误：待填，例如读不到就直接缺件、总额当申请额、材料不完整仍PASS。
- 初审人/独立复核人/日期：待填。
- 分歧与处理：待填；未解决则不计完成。

## 工程执行状态

用例写完可先“业务确认、尚未执行”。代码可用后再记录构建版本、实际输出、PASS/FAIL测试结果、运行ID。**业务确认完成不等于程序测试通过。**第一周不少于60例，发布前每条规则至少6个有意义测试。
