# W3 并行开发契约

更新日期：2026-09-16。  
基线：`main@1b0f08b`（B06 已合入）。  
准备分支：`refactor/w3-review-contract`。

## 1. 目标

W3 的 B07、B08、B09 都只依赖 B06，可以并行开发。并行的边界是“领域提取 + 规则执行器”，不是三条分支同时重写 B06 审查编排和工作台。

本准备分支只建立公共契约和通用结果持久化，不实现 RULE-002/003/004/005/006/010 的业务判定。

## 2. 为什么新增 `review_item_results`

当前数据库通过 `Base.metadata.create_all` 建表，没有迁移框架。`create_all` 能创建缺失表，但不会给已存在的 `review_items` 自动增加新列。因此 W3 不在三条并行分支里分别扩展 `review_items`，而是新增一张一对一结果表：

| 字段 | 说明 |
|---|---|
| `review_item_id` | 主键，同时外键到 `review_items.id`；每个规则条目最多一份通用结果 |
| `payload_json` | `RuleExecutionResult` 的完整 JSON；容纳名称、负责人、预算、日期等不同规则的数据 |
| `created_at` | 首次写入时间 |
| `updated_at` | 最近一次覆盖时间 |

通用结果由 `backend/app/services/review_results.py` 写入。重复计算同一个 `review_item_id` 时执行 upsert，不增加第二行。

## 3. 唯一公共执行器契约

领域规则必须从 `backend/app/review_contract.py` 使用以下对象：

```python
RuleExecutionContext(
    project_id=...,
    review_item_id=...,
    rule_code=...,
    source_rule_id=...,
    version_id=...,
    version_number=...,
    snapshot=...,
)

RuleExecutionResult(
    status="PASS" | "FAIL" | "NEED_HUMAN_REVIEW" | "SYSTEM_ERROR",
    summary="给工作台直接展示的一句话",
    evidence=[...],
    data={...},
)
```

`ReviewEvidence` 是后续原文定位的公共最小结构：

- `material_id` / `category` / `original_filename`
- `field_name`
- `raw_value` / `normalized_value`
- `page_number` / `quote` / `bbox`
- `reliable` / `reason`

规则专有结构放进 `data`，不要给公共表增加规则专属列。

执行器签名统一为：

```python
def execute_xxx_rule(db: Session, context: RuleExecutionContext) -> RuleExecutionResult:
    ...
```

## 4. 状态语义

公共持久化函数 `persist_rule_result` 会同步更新 B06 的 `ReviewItem`：

| 规则结论 | `ReviewItem.status` | 含义 |
|---|---|---|
| `PASS` | `COMPLETED` | 执行完成且通过 |
| `FAIL` | `COMPLETED` | 执行完成但规则不满足；不是系统失败 |
| `NEED_HUMAN_REVIEW` | `PENDING_CONFIRMATION` | 证据不足或语义不确定 |
| `SYSTEM_ERROR` | `FAILED` | 执行器异常或系统级失败 |

领域代码不得自行发明新的工作台状态，也不得把规则 `FAIL` 写成 `FAILED`。

如领域实现发现公共契约不足，先提出契约变更，不在自己的分支直接扩展共享状态或数据库结构。

## 7. 领域分支交付要求

每条分支在交给集成负责人前至少满足：

1. 提取/计算逻辑位于本领域模块，不耦合 `ReviewWorkspace`。
2. 对外执行函数只接收 `Session + RuleExecutionContext`，只返回 `RuleExecutionResult`。
3. 所有可定位字段尽量填 `ReviewEvidence`；读取不可靠时保留原文并说明 `reason`。
4. PASS、FAIL、HUMAN 的边界用单元测试覆盖；不要把“没找到”默认当 FAIL。
5. 不改其他 W3 领域模块。
6. 不提前实现 B11/B12 的通用详情页或人工处置。

## 8. 集成顺序

三条分支可以同时开发。准备 PR 合入后，各分支从最新 `main` 创建。

集成阶段由集成负责人完成：

1. 把 B07/B08/B09 执行器接入 `services/reviews.py`。
2. 统一将每个执行结果写入 `review_item_results`。
3. 在同一 review task 中运行 RULE-002/003/004/005/006/007/010。
4. 统一 API/前端展示通用结果，避免三条分支分别修改工作台。
5. 跑 W3 端到端验收：名称、负责人、经费、预算合计和日期在一次审查中同时核对，刷新后结果仍存在。

## 9. 本准备分支的验收

- 新表可通过现有 `create_all` 初始化，不修改已有 `review_items` 表结构。
- `RuleExecutionResult` 可持久化、读取和覆盖更新。
- 公共状态映射保持 B06 语义：规则 FAIL 是已完成，系统错误才是失败。
- B07/B08/B09 获得固定的输入、输出和证据契约，可以独立开始领域开发。
