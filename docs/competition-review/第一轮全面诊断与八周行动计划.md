# 规证AI：校内比赛功能推进计划

更新日期：2026-09-14。本文沿用原文件路径，内容已按“先完成应用”重写。

## 开发重点

当前最需要的产物是能操作的应用。第一条链路先做到两份材料金额核对、原文定位、问题卡和修改后重审，随后接入政策编辑和更多检查。

产品范围和实现原则以 [参赛方案](../../规证AI_参赛方案.md) 为准。模型通过云端 API 接入，Qwen3.8 视觉能力直接用于功能开发；本地 vLLM 在应用完成后考虑。

文档处理先使用云端多模态 API 与 PDF 原生文本；开发中若完整表格或拍照材料解析成为具体阻塞，再按需接入约 1.2B 参数的 TeleOCR。

## 八周安排

沿用最初的八周规划作为顺序参考，不表示从本次更新日起重新计算比赛剩余时间。每阶段结束应有可操作的功能；遇到阻塞优先修主流程，后续功能随完成情况调整。

| 阶段 | 主要工作 | 可看到的结果 |
|---|---|---|
| W1 | 前后端骨架、云端 API、PDF 上传与预览、申请经费提取和比较 | 两份 PDF → 金额问题卡 → 原文定位 |
| W2 | 政策上传、候选规则编辑、启用规则、保存审查结果 | 可以选择政策规则发起一次审查 |
| W3 | 完整性、名称、负责人、日期、预算等常用检查；扫描页处理 | 主批次材料可集中检查，问题可逐项查看 |
| W4 | 跨文件对比、人工修正、待确认项处理、补正清单 | 用户可以在应用内完成问题处理 |
| W5 | 上传修订版、整包重审、历史结果和问题变化 | 修改前后的问题状态可比较 |
| W6 | 完善页面、文件状态、失败重试、所选批次尚缺功能 | 常用流程连贯，主要功能齐全 |
| W7 | 整体联调、修复阻断问题、部署应用、准备演示材料 | 可从启动应用完整演示到补正重审 |
| W8 | 修复影响展示的问题、整理说明和演示备份 | 可交付的应用和比赛材料 |

应用完成后再决定是否安排本地 vLLM，不为部署模型腾出必须先完成的开发周。更多类别、精细增量重审和复杂 Agent 编排有明确需要时再做。

## 团队协作

原规划为10名开发者，可先按以下工作分配，具体人员随联调需要调整。

| 工作 | 建议人数 | 主要产物 |
|---|---:|---|
| 产品与联调协调 | 1 | 页面流程、任务优先级、跨端问题处理 |
| 前端 | 3 | 上传、规则编辑、审查工作台、原文对比和修订页 |
| 后端 | 3 | 文件、规则、任务、结果与人工操作 API |
| AI与文档处理 | 2 | 模型接入、页面读取、字段及位置提取 |
| 部署与集成 | 1 | 启动配置、应用部署、主流程联调 |

已有科研管理人员可在遇到具体政策歧义时帮助确认，不设固定访谈、标注或每周签字验收任务。

## 开始开发

1. 使用 [现有开发材料](../kickoff/02_政策与材料索引.md)，选出金额一致性所需的申报书与预算内容，准备对应 PDF 输入。
2. 后端通过云端 API 提取两处申请经费和来源位置，程序完成单位换算与比较。
3. 前端展示问题卡与两处原文，接通新版本上传和重审。

现有10条规则和30个场景是可选开发参考，不必先补齐签字表、真实样本配额或所有变体才能编码。

## 比赛展示

展示顺序围绕用户操作：上传材料、发现问题、打开政策和原文、修改材料、重新审查。金额例子可以同时说明单位换算和“申请经费/总经费”的区别。

以实际运行的应用为展示主体，说明当前支持的规则和文件范围。准备一份演示录屏或历史结果作为备用，使用时标明。演示时长按正式赛制安排。
